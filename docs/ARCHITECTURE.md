# dfl — architecture and module contracts

`dfl` ("development flow") is an npm CLI that manages a per-project development
flow: an ordered set of steps (an xstate machine), each step backed by an Agent
Skill rendered from a Handlebars template and installed into the project-level
skill directories of agentic coding tools. A built-in stdio MCP server exposes
the flow to the LLM.

- npm package: `@vishin-pavel/dfl` (GitHub Packages, private), bin: `dfl`
- Runtime: Node >= 22.12, ESM only, TypeScript source in `src/`, bundled to `dist/`
- Per-project data lives in `<project>/.df/`

The name `df` was not used for the binary because `/bin/df` (disk free) exists on
every macOS/Linux machine and the npm global bin precedes `/bin` in `PATH`.

---

## 1. Project layout on disk (`.df/`)

```
<project>/
  .df/
    config.json              # committed  – project config (default active flow, project vars)
    local.json               # ignored    – personal config (agents, personal vars, active flow override)
    state.json               # ignored    – runtime flow state (xstate snapshots + history)
    installed.json           # ignored    – manifest of files dfl wrote outside .df (for clean updates)
    .gitignore               # generated  – ignores the files above and rendered skills
    <flow>/                  # one directory per flow, name = flow id (kebab-case)
      flow.json              # committed  – flow definition (xstate machine config + metadata)
      partials/*.hbs         # committed  – optional Handlebars partials for this flow
      steps/<step>/          # one directory per step, name = xstate state key
        SKILL.md.hbs         # committed  – template of the step's skill
        **/*.md.hbs          # committed  – optional extra templated reference files
        **/*  (non-.hbs)     # committed  – static assets copied verbatim (scripts, json, …)
        SKILL.md, **/*.md    # ignored    – rendered output of the templates
```

Rules:

- Only `*.md.hbs` files are templates. `X.md.hbs` renders to `X.md` next to it.
  Every `.md` file under `.df/*/steps/` is treated as generated and is git-ignored
  (`dfl flow validate` warns about hand-written `.md` files there).
- Reserved names that cannot be flow ids: anything starting with `.` or `_`,
  `config`, `local`, `state`, `installed`, `node_modules`.
- Flow and step ids: `^[a-z0-9]+(-[a-z0-9]+)*$`, max 64 chars (Agent Skills name rules).
- `.df/.gitignore` content (fully owned by dfl, rewritten on every sync):
  ```
  # generated by dfl – do not edit
  local.json
  state.json
  installed.json
  */steps/**/*.md
  ```

### 1.1 `config.json` (committed)

```json
{
  "version": 1,
  "activeFlow": "feature",
  "agents": ["claude"],
  "vars": { "mainBranch": "main" }
}
```

- `activeFlow` – the team default active flow.
- `agents` – optional team-recommended agents (pre-selected by `dfl install`).
- `vars` – project-scoped template variable values.

### 1.2 `local.json` (ignored, personal)

```json
{
  "version": 1,
  "activeFlow": "bugfix",
  "agents": ["claude", "cursor"],
  "vars": { "reviewer": "pavel" }
}
```

Effective active flow = `local.activeFlow ?? config.activeFlow ?? (only flow if exactly one)`.
`dfl flow use <name>` writes `local.json`; `dfl flow use <name> --project` writes `config.json`.

### 1.3 `state.json` (ignored)

```json
{
  "version": 1,
  "flows": {
    "feature": {
      "current": "implement-feature",
      "done": false,
      "snapshot": { "...": "xstate persisted snapshot" },
      "history": [{ "from": "plan-feature", "to": "implement-feature", "event": "NEXT", "at": "2026-09-30T10:00:00.000Z" }],
      "updatedAt": "2026-09-30T10:00:00.000Z"
    }
  }
}
```

State is stored per flow; switching flows keeps each flow's position.
If the stored snapshot no longer matches the machine (step deleted/renamed), the
state falls back to the machine's initial state and a warning is reported.

### 1.4 `installed.json` (ignored)

```json
{
  "version": 1,
  "flow": "feature",
  "agents": ["claude", "cursor"],
  "skills": [{ "agent": "claude", "name": "plan-feature", "dir": ".claude/skills/plan-feature", "files": ["SKILL.md"] }],
  "mcp": [{ "agent": "claude", "file": ".mcp.json", "server": "dfl" }],
  "gitignore": [".claude/skills/plan-feature/"]
}
```

Every sync computes the new set of skill dirs, removes dirs listed in the previous
manifest that are no longer wanted (deleted steps, switched flow, removed agent),
then writes the new manifest. dfl never deletes a directory it did not create
(it is only deleted if it is in the manifest).

## 2. Flow definition (`.df/<flow>/flow.json`)

A flow is an xstate v5 machine config (JSON, flat: atomic + final states only)
wrapped with metadata. Each atomic state is a step; final states are terminal
markers and have no skill.

```json
{
  "name": "feature",
  "title": "Feature development",
  "description": "From spec to shipped PR.",
  "version": "1.0.0",
  "skillPrefix": "",
  "vars": {
    "mainBranch": { "description": "Default branch PRs target", "default": "main", "scope": "project" },
    "reviewer":   { "description": "Your GitHub handle for review requests", "scope": "personal", "required": false }
  },
  "machine": {
    "id": "feature",
    "initial": "spec-feature",
    "states": {
      "spec-feature":      { "description": "Write a feature spec", "meta": { "title": "Spec" }, "on": { "NEXT": "plan-feature" } },
      "plan-feature":      { "description": "…", "meta": { "title": "Plan" }, "on": { "NEXT": "implement-feature", "BACK": "spec-feature" } },
      "implement-feature": { "description": "…", "meta": { "title": "Implement" }, "on": { "NEXT": "review-feature" } },
      "review-feature":    { "description": "…", "meta": { "title": "Review" }, "on": { "NEXT": "ship-feature", "CHANGES_REQUESTED": "implement-feature" } },
      "ship-feature":      { "description": "…", "meta": { "title": "Ship" }, "on": { "NEXT": "done" } },
      "done":              { "type": "final", "description": "Feature shipped" }
    }
  }
}
```

- Transition values: a target state key string, or `{ "target": "...", "description": "..." }`.
- `NEXT` is the conventional "forward" event; step ordering for lists/views is a
  traversal from `initial` that follows `NEXT` first, then other events in
  declaration order (BFS), then unreachable states in declaration order.
- `skillPrefix` is prepended to step ids to form skill names (`skillName = skillPrefix + stepId`).
- Guards/actions/nested/parallel states are not supported (validation error).
- `vars.*.scope`: `project` values live in `config.json`, `personal` values in `local.json`.

### 2.1 Validation (`validateFlow`)

Errors: invalid JSON/schema; `name` ≠ directory; invalid ids; `initial` missing;
transition target missing; nested `states`/`type: parallel`/guards; xstate
`createMachine` throws; non-final state without `steps/<id>/SKILL.md.hbs`.
Warnings: state unreachable from `initial`; no final state reachable; hand-written
`.md` in steps; step dir without a state; skill name collides with a built-in skill.

## 3. Templates

Handlebars 4 (`noEscape: true`, non-strict), one environment per render with:

**Context**

```ts
{
  project: { name: string; root: string },          // name = basename(root)
  flow:    { name, title, description, skillPrefix, initial, steps: StepContext[] },
  step:    StepContext,                              // the step being rendered (built-ins: undefined)
  vars:    Record<string, unknown>,                  // defaults < config.vars < local.vars < DFL_VAR_<NAME> env
  env:     Record<string, string>,                   // process.env
  dfl:     { version: string, mcpServer: 'dfl' },
}
StepContext = { id, skillName, title, description, index, number /*1-based*/, final,
                next: StepRef[] /* transitions */, prev: StepRef[] /* incoming */ }
StepRef     = { event, id, skillName, title }
```

**Helpers**: `eq ne and or not` (logic), `default value fallback`, `upper lower kebab title`,
`json value`, `join array sep`, `indent n text`.

**Partials** (registered globally, overridable by `.df/<flow>/partials/<name>.hbs`):
- `{{> flow-context}}` – a "Where this step sits in the flow" section: flow title,
  step n/total, previous/next steps with their slash commands, and the MCP
  instructions (`get_status` at start, `complete_step` / `transition` when done).

**Frontmatter**: after rendering `SKILL.md`, dfl normalises the YAML frontmatter:
`name` is forced to `skillName`; `description` defaults to the state `description`
(or `title`) when missing; other keys are preserved. Descriptions are truncated to
1024 chars.

## 4. Agents

`src/agents/registry.ts` holds one `AgentAdapter` per supported tool. See
`docs/AGENTS.md` for the researched paths per tool.

```ts
interface AgentAdapter {
  id: AgentId;
  name: string;                         // display name
  skillsDir: string | null;             // project-relative dir that holds <skill>/SKILL.md, null if unsupported
  commandsDir?: string;                 // fallback slash-command dir when skills are unsupported
  renderCommand?(skill: RenderedSkill): { file: string; content: string }; // fallback format
  mcp?: McpTarget;                      // project-level MCP config target (absent → print manual instructions)
  detect(root: string): boolean;        // project already uses this tool
  invocation(skillName: string): string // how the user invokes a skill, e.g. "/plan-feature"
}
interface McpTarget {
  file: string;                         // project-relative config path
  format: 'json' | 'jsonc' | 'toml';
  upsert(root: string, server: McpServerSpec): void;   // idempotent, preserves unrelated content/comments
  remove(root: string, name: string): void;
}
interface McpServerSpec { name: 'dfl'; command: string; args: string[]; env?: Record<string, string> }
```

Several adapters may share a skills dir (e.g. `.agents/skills`) or MCP file
(`.mcp.json`); the installer writes each distinct directory/file once.

| id | tool | skills dir | invoke | project MCP config |
|----|------|-----------|--------|--------------------|
| `claude` | Claude Code | `.claude/skills` | `/name` | `.mcp.json` → `mcpServers` (`type: "stdio"`) |
| `cursor` | Cursor | `.cursor/skills` | `/name` | `.cursor/mcp.json` → `mcpServers` (`type: "stdio"`) |
| `antigravity` | Google Antigravity | `.agents/skills` | `/name` | `.agents/mcp_config.json` → `mcpServers` |
| `codex` | OpenAI Codex | `.agents/skills` | `$name` | `.codex/config.toml` → `[mcp_servers.dfl]` (trusted projects only) |
| `gemini` | Gemini CLI | `.gemini/skills` | `/name` | `.gemini/settings.json` (JSONC) → `mcpServers` |
| `copilot` | GitHub Copilot | `.github/skills` | `/name` | `.mcp.json` → `mcpServers` |
| `windsurf` | Windsurf / Devin Desktop | `.devin/skills` | `/name` | `.devin/mcp_config.json` → `mcpServers` |
| `opencode` | OpenCode | `.opencode/skills` | `/name` | `opencode.json` → `mcp.dfl = { type: "local", command: ["dfl","mcp"], enabled: true }` |
| `kiro` | Kiro | `.kiro/skills` | `/name` | `.kiro/settings/mcp.json` → `mcpServers` |

Portable SKILL.md frontmatter: only `name`, `description`, `license`, `compatibility`,
`metadata` (string→string map) and `allowed-tools`. dfl adds
`metadata: { dfl-flow: <flow>, dfl-step: <step> }`. Template bodies must avoid literal
`$ARGUMENTS`, `$1`…, lines starting with ``!` `` and `@word` tokens (they are expanded
by Claude Code / OpenCode when a skill runs as a slash command).

**MCP command resolution**: if the running `dfl` lives inside
`<root>/node_modules`, the server spec is `{ command: "npx", args: ["--no-install", "dfl", "mcp"] }`,
otherwise `{ command: "dfl", args: ["mcp"] }`. Overridable via `config.json` `mcp.command`/`mcp.args`.
The MCP server finds the project root via: `--root` flag → `DFL_ROOT` env → MCP
client `roots` (first `file://` root containing `.df/`) → nearest ancestor of cwd with `.df/`.

## 5. Sync pipeline (`install` / `flow-update` / `flow use`)

`syncProject(paths, opts)` is the single code path that writes outside `.df/`:

1. Resolve active flow + agents (`opts.agents ?? local.agents ?? config.agents`).
2. Resolve vars; missing required vars → `opts.promptVar(def)` (interactive) or error.
3. Render the active flow: every `steps/**/*.md.hbs` → `.md` (inside `.df`).
4. Render built-in skills from the package (`templates/builtin-skills/*`) in memory.
5. For every agent: copy each step dir (rendered `.md` + static non-`.hbs` files)
   into `<skillsDir>/<skillName>/`, plus built-ins; or write fallback command files.
6. Remove stale dirs from the previous manifest; write the new manifest.
7. Upsert the MCP server entry into each agent's project MCP config (unless `--no-mcp`).
8. Rewrite `.df/.gitignore`; upsert a managed block in `<root>/.gitignore`
   listing the installed skill dirs (they contain personal config):
   ```
   # >>> dfl (managed) >>>
   .claude/skills/plan-feature/
   # <<< dfl (managed) <<<
   ```

`uninstall` removes everything in the manifest, the MCP entries and the managed
`.gitignore` block; `--purge` also deletes `.df/local.json`, `state.json`, rendered files.

## 6. CLI

```
dfl install [--agents a,b] [--flow <tpl-or-name>] [--yes] [--no-mcp] [--root <dir>]
dfl uninstall [--purge]
dfl flow-update                      # alias: dfl update – re-render + re-install (after git pull / edits)
dfl status                           # active flow, current step, available events
dfl next [event]                     # fire event (default NEXT)
dfl goto <step>                      # jump to a step
dfl reset                            # back to initial
dfl flow list | templates
dfl flow use <name> [--project]
dfl flow create <name> [--from <template>] [--title <t>]
dfl flow import <git-url|github:owner/repo[/path][#ref]|path> [--name <n>]
dfl flow delete <name> [--yes]
dfl flow validate [name]
dfl flow view [name] [--zoom <0-3>] [--print]
dfl step list [--flow <f>]
dfl step add <id> [--after <step>|--before <step>] [--title] [--description] [--event NEXT]
dfl step edit <id> [--title] [--description] [--rename <new-id>]
dfl step remove <id> [--force]
dfl step transition <id> <event> <target|--remove>
dfl vars list | set <key> <value> [--personal]
dfl agents                           # supported agents, detection, where skills go
dfl mcp [--root <dir>]               # stdio MCP server
```

Rich output: `@clack/prompts` for wizards/spinners/notes, `picocolors` for colour,
Ink (React) for the full-screen flow viewer. All commands work non-interactively
(`--yes`, or when stdin is not a TTY) and exit non-zero on error.

### 6.1 Flow viewer (`dfl flow view`)

Full-screen Ink app (alternate screen). The flow graph is laid out once per zoom
level into a character canvas; the viewport shows the part that fits the
terminal (minus a 1-line header and 1-line footer) and follows resizes.

| key | action |
|-----|--------|
| `w` `a` `s` `d` | pan up / left / down / right by one step cell (node pitch) |
| `q` | zoom in (more detail) |
| `e` | zoom out (less detail) |
| `x` | exit (Ctrl+C also exits) |

Layout: elkjs `layered` + orthogonal routing laid out in terminal cells, drawn on a
character canvas (see the prototype in the research notes). Zoom levels:
`0` one-line `[Title…]` nodes, `1` 3-row boxes with the title, `2` cards with title +
wrapped description, `3` cards with title + description + skill command and events.
Default zoom = the highest level whose canvas fits the terminal, min 1.
The current step is drawn with a heavy border. Non-TTY or `--print` prints the
whole canvas. `l` toggles top-to-bottom / left-to-right, `c` centers the current step.
Uppercase `W A S D` pan a full page.

## 7. MCP server (`dfl mcp`)

Server name `dfl`, built on `@modelcontextprotocol/server` v2 (zod 4 schemas).
Files are re-read on every call (no caching), so edits and `git pull` are picked up
immediately. Mutating tools run `syncProject` (non-interactive) afterwards and report
the sync summary. Tools (all return JSON text + `structuredContent`):

| tool | purpose |
|------|---------|
| `get_flow` | active (or named) flow: steps in order, transitions, vars, current step |
| `list_flows` | all flows + which is active |
| `get_status` | current step, its skill command, available events, history tail |
| `get_step` | one step: metadata, transitions, template path, rendered skill text |
| `transition` | fire an event (default `NEXT`) → new current step |
| `complete_step` | shorthand for `transition NEXT` from a given step (checks it is current) |
| `goto_step` | jump to a step |
| `add_step` | create step (dir + SKILL.md.hbs + machine wiring), then re-sync |
| `update_step` | change title/description/template/transitions/rename, then re-sync |
| `delete_step` | delete step, rewire transitions, then re-sync |
| `validate_flow` | validation issues |
| `sync` | same as `dfl flow-update` |

Resources: `dfl://flow` (active flow JSON), `dfl://steps/{id}` (step template).

## 8. Source layout and module ownership

```
src/
  cli.ts                 # bin entry → run.ts
  run.ts                 # runCli(argv): error handling / exit codes
  program.ts             # buildProgram(): commander tree
  commands/*.ts          # one file per command group (install, flow, step, state, vars, agents, mcp)
  ui/*.ts                # output helpers (picocolors), clack prompt wrappers, tables
  core/
    types.ts             # shared types (all modules)
    errors.ts ids.ts fsx.ts paths.ts config.ts gitignore.ts flow.ts   # infra + flow model
    machine.ts           # xstate runtime state
    validate.ts          # flow validation
    steps.ts             # step CRUD
    vars.ts render.ts    # template variables + Handlebars rendering
    sync.ts              # install/sync orchestrator + manifest
    import.ts            # git/local flow import
  agents/
    types.ts registry.ts mcp-config.ts
  mcp/server.ts          # MCP server
  tui/
    graph/*.ts           # elkjs layout + canvas rasterizer
    FlowView.tsx         # Ink viewer component
    run-flow-view.tsx    # entry for `dfl flow view`
templates/
  flows/<name>/flow.json + steps/<step>/SKILL.md.hbs   # prebuilt flows
  skills/<name>/SKILL.md.hbs                          # built-in skills
  partials/*.hbs                                      # built-in partials (flow-context)
test/                    # vitest; helpers in test/helpers
```

Conventions: ESM, relative imports end in `.js`, user-facing errors are `DflError`
(message + optional hint), nothing in `core/`, `agents/` or `mcp/` writes to stdout,
Ink/React are only imported lazily by `flow view`.
