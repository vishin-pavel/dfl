# dfl — architecture and module contracts

`dfl` ("development flow") is an npm CLI that manages a per-project development
flow: an ordered set of steps (an xstate machine), each step backed by an Agent
Skill rendered from a Handlebars template and installed into the project-level
skill directories of agentic coding tools. A built-in stdio MCP server exposes
the flow to the LLM.

- npm package: `@vishin-pavel/dfl` (GitHub Packages, private), bin: `dfl`
- Runtime: Node >= 22.12 (`src/cli.ts` checks the version before importing anything else and exits
  with a clear message on older Node). Building needs Node >= 22.18 (or >= 24.11): tsdown 0.23
  cannot load `tsdown.config.ts` on older versions.
- ESM only, TypeScript source in `src/`, bundled to `dist/`
- Per-project data lives in `<project>/.df/`

The name `df` was not used for the binary because `/bin/df` (disk free) exists on
every macOS/Linux machine and the npm global bin precedes `/bin` in `PATH`.

## 1. Project layout on disk (`.df/`)

```
<project>/
  .df/
    config.json              # committed  – project config (default active flow, project vars, MCP override)
    local.json               # ignored    – personal config (agents, personal vars, active flow override, MCP preference)
    state.json               # ignored    – runtime flow state (current step + history per flow)
    installed.json           # ignored    – manifest of what dfl wrote (skill dirs, MCP entries, rendered files)
    .gitignore               # generated  – ignores the files above, rendered skills, .dfl-*/ and .lock
    .lock                    # transient  – held while a dfl process changes the project (§6.2)
    .dfl-stage-*/            # transient  – staging dirs of a flow import / pull
    <flow>/                  # one directory per flow, name = flow id (kebab-case) = flow.json "name"
      flow.json              # committed  – flow definition (xstate machine config + metadata)
      partials/*.hbs         # committed  – optional Handlebars partials for this flow
      steps/<step>/          # one directory per step, name = xstate state key
        SKILL.md.hbs         # committed  – template of the step's skill
        **/*.md.hbs          # committed  – optional extra templated reference files
        **/*  (non-.hbs)     # committed  – static assets copied verbatim (scripts, json, …)
        SKILL.md, **/*.md    # ignored    – rendered output of the templates
```

Rules:

- Only `*.md.hbs` files are templates. `X.md.hbs` renders to `X.md` next to it. Other `*.hbs`
  files under `steps/` are neither rendered nor copied (validation warning).
- Every `.md` file under `.df/*/steps/` is git-ignored. dfl deletes one only when it rendered it
  itself (listed in the manifest's `rendered`, §1.4) and its template is gone; a hand-written `.md`
  is kept (also by `flow pull` / `flow import --force`, which carry it into the new files), not
  installed, and reported by `dfl flow validate`.
- Flow and step ids: `^[a-z0-9]+(-[a-z0-9]+)*$`, max 64 chars (Agent Skills name rules). A step id
  cannot be only digits (`1`, `007`): JavaScript lists such object keys first, so `machine.states`
  could not keep the flow order (§2); `validateFlow` reports existing ones.
  Reserved flow names: `config`, `local`, `state`, `installed`, `node-modules`, `steps`, `partials`.
- Flow names are validated wherever a name becomes a path (`assertValidFlowName`, and
  `assertPathSegment` in every `ProjectPaths` builder): `flowExists` is false for invalid names,
  `readFlowDefinition`/`loadFlow`/`deleteFlow`/`copyFlowFromDir`/`setActiveFlow` throw
  `INVALID_NAME`, `listFlows` and the active-flow lookup skip invalid directory names. flow.json
  `name` must equal the directory name (`readFlowDefinition` throws `INVALID_FLOW` with a hint;
  `validateFlow` reports it).
- `.df/.gitignore` content (fully owned by dfl, rewritten on every sync):
  ```
  # generated by dfl – do not edit
  # personal config, runtime state and install manifest
  local.json
  state.json
  installed.json
  # skills rendered from *.md.hbs templates (may contain personal values)
  */steps/**/*.md
  # temporary dirs of an interrupted flow import
  .dfl-*/
  # held while a dfl process changes the project
  .lock
  ```

### 1.1 `config.json` (committed)

```json
{
  "version": 1,
  "activeFlow": "feature",
  "agents": ["claude"],
  "vars": { "mainBranch": "main" },
  "mcp": { "command": "pnpm", "args": ["exec", "dfl", "mcp"] }
}
```

- `activeFlow` – the team default active flow. `dfl install` sets it only when it is missing and the
  choice is not arbitrary (flows created in this run, `--flow`, a wizard choice or the only flow);
  `dfl flow use <name> --project` changes it.
- `agents` – optional team-recommended agents (pre-selected by `dfl install`).
- `vars` – project-scoped template variable values (shared by all flows).
- `mcp` – optional override of the MCP server command (§4.1).

### 1.2 `local.json` (ignored, personal)

```json
{
  "version": 1,
  "activeFlow": "bugfix",
  "agents": ["claude", "cursor"],
  "vars": { "reviewer": "pavel" },
  "mcp": false
}
```

Effective active flow = `local.activeFlow ?? config.activeFlow ?? (only flow if exactly one)`;
names that do not exist on disk (or are invalid) are skipped.
`dfl flow use <name>` writes `local.json`; `dfl flow use <name> --project` writes `config.json`.
`mcp` is the personal MCP preference (§5): `dfl install --no-mcp` (or answering no) stores
`false`, `--mcp` (or yes) stores `true`; missing means `true`.

### 1.3 `state.json` (ignored)

```json
{
  "version": 1,
  "flows": {
    "feature": {
      "current": "implement-feature",
      "history": [{ "from": "plan-feature", "to": "implement-feature", "event": "NEXT", "at": "2026-09-30T10:00:00.000Z" }],
      "updatedAt": "2026-09-30T10:00:00.000Z"
    }
  }
}
```

State is stored per flow; switching flows keeps each flow's position. Only the
current state key is stored (`done` is derived from the machine). History is
chronological and capped at 200 entries. If the stored step no longer exists
(deleted/renamed outside dfl), the state falls back to the machine's initial state
and `repaired` explains it (the CLI prints it, `--json` and MCP results carry it); a corrupt
`state.json` is ignored and rewritten. dfl's own edits keep the position valid: a renamed step
keeps its position, and removing the current step moves it (to the removed step's `NEXT` target,
else the step that led to it, else the initial step) with a `STEP_REMOVED` history entry. A
`flow pull` / `flow import --force` whose new version lacks the current step moves it the same way
(first surviving step on its old `NEXT` path, else the nearest earlier surviving step, else the
initial step).

### 1.4 `installed.json` (ignored)

```json
{
  "version": 1,
  "flow": "feature",
  "agents": ["claude", "cursor"],
  "skills": [{ "agents": ["claude"], "name": "plan-feature", "dir": ".claude/skills/plan-feature", "files": ["SKILL.md"] }],
  "mcp": [{ "agents": ["claude"], "file": ".mcp.json", "server": "dfl", "createdFile": true, "createdContainer": true }],
  "rendered": [".df/feature/steps/plan-feature/SKILL.md"],
  "dflVersion": "0.1.0",
  "fingerprint": "5c1f…"
}
```

- `skills` – every skill dir dfl wrote and the files it wrote there (the `.gitignore` marker is
  implied).
- `mcp` – MCP config files that hold dfl's `dfl` entry; `createdFile`/`createdContainer` record
  whether dfl created the file / the servers container, so uninstall removes only those (a file that
  existed before, even blank, is never deleted).
- `rendered` – project-relative `.md` files dfl rendered under `.df/<flow>/steps/`; only these are
  ever deleted as stale output (§5).
- `createdDirs` – dirs dfl created on the way to a skills dir or MCP file (`.claude`,
  `.kiro/settings`, …; only ancestors of adapter paths are accepted). Emptied parent dirs are removed
  only when listed here (OS junk such as `.DS_Store` does not keep them), so an agent dir that
  existed before dfl (e.g. an empty `.kiro/`) stays.
- `skippedDirs` – skills dirs the last sync skipped because they are (or lie under) a symlink: those
  agents have no skills, and `checkSyncState` reports it.
- `fingerprint` – see §5.1. `dflVersion` – the version that wrote the manifest.
- `uninstalled: true` – set when `dfl uninstall` keeps the manifest only to retry MCP entries it
  could not remove; the project then counts as not installed (§5.2).

The existence of the manifest means "this developer ran `dfl install`" (`isInstalledForUser`):
mutations only auto-sync then (§5.2). A manifest that lists neither agents nor skills (written by
`dfl flow-update` in a fresh clone without selected agents) does not count.

The manifest is **untrusted input** (it can be hand-edited or force-committed). `loadManifest`
drops, with a warning, every skill entry whose `dir` is not `<adapter skillsDir>/<valid id>` for a
known adapter, file names that are not plain relative paths (no `..`, no absolute paths), MCP entries
for files that are not a known adapter MCP config or for a server other than `dfl`, and `rendered`
paths outside `.df/<flow>/steps/**/*.md`. Structurally malformed or unreadable manifests (invalid
JSON) throw `INVALID_MANIFEST` with the hint to delete the file and run `dfl install` again.

**Ownership.** A skill dir is dfl's when it holds the marker `.gitignore` (first line
`# generated by dfl – …`) or its `SKILL.md` frontmatter has a `metadata` key starting with `dfl-`
(a marker dir whose `SKILL.md` has no dfl metadata counts as the user's). dfl never overwrites an
existing skill dir it does not own (warning, skipped). When a dir is no longer produced, dfl deletes
only the files the manifest lists for it plus the marker, then removes the dir only if it is empty
(OS junk such as `.DS_Store` and `Thumbs.db` does not count and goes with it); otherwise it keeps the
dir and warns.

**Symlinks.** Nothing is written or deleted through a symbolic link: every path component below
the project root is `lstat`ed first, and a symlink makes dfl skip that skill dir / MCP file with a
warning. Files are written through a temp file (`O_EXCL`) and renamed into place.

**Git.** Every installed skill dir gets the marker file `.gitignore`:

```
# generated by dfl – this skill is rendered from .df templates and may contain personal values
*
```

so git ignores the whole dir (marker included). dfl never writes a managed block into the root
`.gitignore`; a sync (and uninstall) removes a legacy `# >>> dfl (managed) >>>` block, tolerating a
missing end marker without deleting user lines. A root `.gitignore` that is a symlink is never
replaced or written through: dfl warns that the block must be removed by hand.

## 2. Flow definition (`.df/<flow>/flow.json`)

A flow is an xstate v5 machine config (JSON, flat: atomic + final states only)
wrapped with metadata. Each atomic state is a step; final states are terminal
markers and have no skill.

```json
{
  "name": "feature",
  "title": "Feature development",
  "description": "From spec to shipped PR.",
  "version": "1.0.0",
  "skillPrefix": "",
  "source": { "type": "git", "ref": "https://github.com/acme/flows.git", "path": "flows/feature", "rev": "v1", "commit": "3f2a…" },
  "vars": {
    "mainBranch": { "description": "Default branch PRs target", "default": "main", "scope": "project" },
    "reviewer":   { "description": "Your GitHub handle for review requests", "scope": "personal", "required": false }
  },
  "machine": {
    "id": "feature",
    "initial": "spec-feature",
    "states": {
      "spec-feature":      { "description": "Write a feature spec", "meta": { "title": "Spec" }, "on": { "NEXT": "plan-feature" } },
      "plan-feature":      { "description": "…", "meta": { "title": "Plan" }, "on": { "NEXT": "implement-feature", "BACK": "spec-feature" } },
      "implement-feature": { "description": "…", "meta": { "title": "Implement" }, "on": { "NEXT": "review-feature" } },
      "review-feature":    { "description": "…", "meta": { "title": "Review" }, "on": { "NEXT": "ship-feature", "CHANGES_REQUESTED": { "target": "implement-feature", "description": "Reviewers asked for changes" } } },
      "ship-feature":      { "description": "…", "meta": { "title": "Ship" }, "on": { "NEXT": "done" } },
      "done":              { "type": "final", "description": "Feature shipped" }
    }
  }
}
```

- Transition values: a target state key string, or `{ "target": "...", "description": "..." }`
  (the condition for firing the event, shown to the agent by the flow-context partial). Only
  `target`, `description` and `meta` are allowed in the object form; arrays of transitions are not
  supported.
- **Flow order** (lists, `step n of m`, `flow.steps`, the viewer) is the declaration order of
  `machine.states`, with the initial state moved first and final states moved last (stable;
  `orderStates` in `flow.ts`). `addStep` inserts the new key at its position so the order follows.
- `NEXT` is the conventional "forward" event; `addStep` without a position appends to the end of
  the `NEXT` path from `initial`, `removeStep` reroutes through `NEXT`.
- `skillPrefix` is prepended to step ids to form skill names (`skillName = skillPrefix + stepId`).
- Guards/actions/nested/parallel states are not supported (validation error).
- `vars.*.scope`: `project` values live in `config.json`, `personal` values in `local.json`.
- `source` records where the flow came from: `template` (`ref` = template name), `git` (`ref` =
  URL, optional `path`, `rev`, and the imported `commit`), `local` (`ref` = directory as a posix path
  relative to the project root, never absolute), or `created`. `dfl flow pull` uses it (§6).
- Parsing keeps key order (`parseFlowDefinition` returns the input object), so a no-op edit
  rewrites flow.json byte for byte.

### 2.1 Validation (`validateFlow`)

Errors: invalid JSON/schema; `name` ≠ directory; invalid or reserved names; invalid ids and skill
names, duplicate skill names, a skill name that collides with a built-in dfl skill; `initial`
missing; the initial state is final while real steps exist; transition target missing, empty
target, unknown keys in a transition object, invalid/wildcard/`xstate.*` event names; nested
`states`/`type: parallel`/guards/actions; xstate `createMachine` throws; non-final state without
`steps/<id>/SKILL.md.hbs`; a template (`steps/**/*.md.hbs`) or flow partial (`partials/**/*.hbs`)
that does not parse with the dfl Handlebars environment (reported with file and line); an unknown
`{{> partial}}` reference.

Warnings: state unreachable from `initial`; no final state reachable; dead-end step; a step name
that shadows a built-in agent command (`review`, `plan`, …); a step template expression whose first
name is neither a context root (§3) nor a helper, outside `each`/`with` blocks (e.g. an unescaped
GitHub Actions `${{ secrets.X }}`, which renders empty); a `.md` file in steps without a template
(stale dfl output, or hand-written); a non-`.md` `.hbs` file under steps; a step dir without a
state; a final state with a steps dir.

Step mutations (§2.2) validate the edited definition before writing and are refused
(`INVALID_FLOW`) only for errors they introduce; errors the flow already had are returned as
`remainingErrors` (compared by kind and step ids, not message text), so a broken flow can be
repaired one edit at a time.

### 2.2 Step CRUD (`steps.ts`)

- `addStep(paths, flow, { id, after?, before?, event?, on?, template?, … })` – `after X`: `X`'s
  `event` transition leads to the new step, which inherits the old target; `before X`: every
  `event` transition into `X` is redirected (only a `NEXT` insert before the initial step moves
  `initial`; nothing to rewire → `INVALID_POSITION`); neither: after the last step on the `NEXT`
  path (`placement.auto`). Returns the model plus `placement` and `remainingErrors`. The template
  must parse (`INVALID_TEMPLATE`, nothing written); when flow.json cannot be written, the new step
  directory is removed again.
- `updateStep(…, { title?, description?, template?, rename?, on?, initial? })` – `on` values are
  `string | { target, description? } | null` (a string keeps an existing description, `''` removes
  it, `null` removes the event). A final state cannot become initial (`FINAL_STEP`).
- `setTransition(paths, flow, id, event, target | null, description?)`.
- `removeStep(…, { force? })` – reroutes incoming transitions to the removed step's `NEXT` target
  (`rewired`); a rerouted transition that would point at its own source is removed (`dropped`,
  reason `self-loop`); without `NEXT`: `CANNOT_REWIRE` unless `force` (dropped, reason `no-next`);
  the last step: `LAST_STEP`. Also returns `initialMoved`, `currentMoved`. `planRemoveStep` is the
  same computation without writing (the CLI reports refusals before asking for confirmation).

## 3. Templates

Handlebars 4 (`noEscape: true`, non-strict), one environment per render (`createHandlebars`) with:

**Context**

```ts
{
  project: { name: string; root: string },          // name = basename(root)
  flow:    { name, title, description, skillPrefix, initial, stepCount, steps: StepContext[] },
  step:    StepContext,                              // the step being rendered (built-ins: undefined)
  vars:    Record<string, unknown>,                  // defaults < config.vars < local.vars < DFL_VAR_<NAME> env
  env:     Record<string, string>,                   // only DFL_ENV_<NAME> variables, as env.<NAME>
  dfl:     { version: string, mcpServer: 'dfl', cli: string },   // cli: dflLauncher (§4.1)
}
StepContext = { id, skillName, title, description, index, number /*1-based*/, final,
                next: StepRef[] /* transitions */, prev: StepRef[] /* incoming */ }
StepRef     = { event, id, skillName, title, final, description }
```

Templates never see the rest of the process environment (it could leak secrets into rendered,
possibly shared files).

**Helpers**: `eq ne and or not` (logic, also as block helpers: `{{#eq a b}}…{{else}}…{{/eq}}`),
`default value fallback`, `upper lower kebab title`, `json value [spaces]`, `join array sep`,
`indent n text` (also block form), `command skillName` (`/name`), `handle value` (drops leading
`@` and whitespace, for `gh --reviewer`). The built-in `log` helper is overridden to write to
**stderr** (stdout carries the MCP JSON-RPC stream) and renders nothing.

**Partials** (registered globally, overridable by `.df/<flow>/partials/<name>.hbs`):
- `{{> flow-context}}` – a "Flow context" section: flow title, step n/total, the step it comes
  after (`NEXT` arrivals) and the steps that also lead to it (other events, with their
  descriptions), the MCP instructions (`get_status` with `{"flow": …}` at start, `complete_step` /
  `goto_step` with `"flow"` when done) and CLI fallbacks with `--flow`, so a skill keeps acting on
  its own flow even when another flow is active.

**Frontmatter**: after rendering `SKILL.md`, dfl normalises the YAML frontmatter:
`name` is forced to `skillName`; `description` defaults to the state `description`
(or `title`) when missing; `metadata` gets `dfl-flow`/`dfl-step` (built-ins: `dfl-builtin`); other
keys are preserved. Descriptions are truncated to 1024 chars.

**Validation**: `validateFlow` compiles every `*.md.hbs` and flow partial with the dfl environment
(§2.1); `addStep`/`updateStep` reject a template that does not parse before writing anything.

## 4. Agents

`src/agents/registry.ts` holds one `AgentAdapter` per supported tool. See
[`docs/AGENTS.md`](AGENTS.md) for the researched paths per tool. The list is closed (9 adapters);
custom skills dirs / MCP files are not configurable yet.

```ts
interface AgentAdapter {
  id: AgentId;
  name: string;                         // display name
  skillsDir: string;                    // project-relative dir that holds <skill>/SKILL.md
  invocation(skillName: string): string // how the user invokes a skill, e.g. "/plan-feature", "$plan-feature"
  detect(root: string): boolean;        // project already uses this tool
  mcp?: McpTarget;                      // project-level MCP config target (absent → manual instructions)
  mcpNote?: string;                     // extra MCP instructions (trust, approval, reload)
  mcpCwdOutsideWorkspace?: boolean;     // some clients start servers outside the project (npx entry caveat)
  notes?: string; docs?: string;        // shown by `dfl agents`
}
interface McpTarget {
  file: string;                         // project-relative config path
  format: 'json' | 'jsonc' | 'toml';
  upsert(root, spec): boolean;          // idempotent, preserves unrelated content/comments
  plan(root, spec): 'added' | 'updated' | 'unchanged';   // dry run of upsert
  remove(root, name, { deleteEmptyFile?, dropEmptyContainer?, file? }?): boolean;
  has(root, name): boolean;
  read(root, name, file?): { command, args } | undefined;
  inspect(root): { file, exists, container };            // what dfl would create
}
interface McpServerSpec { name: 'dfl'; command: string; args: string[]; env?: Record<string, string> }
```

Several adapters may share a skills dir (e.g. `.agents/skills`) or MCP file
(`.mcp.json`); the installer writes each distinct directory/file once.

| id | tool | skills dir | invoke | project MCP config |
|----|------|-----------|--------|--------------------|
| `claude` | Claude Code | `.claude/skills` | `/name` | `.mcp.json` → `mcpServers` (`type: "stdio"`) |
| `cursor` | Cursor | `.cursor/skills` | `/name` | `.cursor/mcp.json` → `mcpServers` (`type: "stdio"`) |
| `antigravity` | Google Antigravity | `.agents/skills` | `/name` | `.agents/mcp_config.json` → `mcpServers` |
| `codex` | OpenAI Codex | `.agents/skills` | `$name` | `.codex/config.toml` → `[mcp_servers.dfl]` (trusted projects only) |
| `gemini` | Gemini CLI | `.gemini/skills` | `/name` | `.gemini/settings.json` (JSONC) → `mcpServers` |
| `copilot` | GitHub Copilot | `.github/skills` | `/name` | `.mcp.json` → `mcpServers` |
| `windsurf` | Windsurf / Devin Desktop | `.devin/skills` | `/name` | `.devin/mcp_config.json` → `mcpServers` |
| `opencode` | OpenCode | `.opencode/skills` | `/name` | `opencode.json` → `mcp.dfl = { type: "local", command: ["dfl","mcp"], enabled: true }` |
| `kiro` | Kiro | `.kiro/skills` | `/name` | `.kiro/settings/mcp.json` → `mcpServers` |

Portable SKILL.md frontmatter: only `name`, `description`, `license`, `compatibility`,
`metadata` (string→string map) and `allowed-tools`. dfl adds
`metadata: { dfl-flow: <flow>, dfl-step: <step> }`. Template bodies must avoid literal
`$ARGUMENTS`, `$1`…, lines starting with ``!` `` and `@word` tokens (they are expanded
by Claude Code / OpenCode when a skill runs as a slash command); `renderFlow` warns when a
rendered `SKILL.md` contains one (`slashCommandTokens`; `@word` only outside code fences), which
catches variable values too.

### 4.1 Launcher and MCP command (`dflLauncher`, `resolveMcpServerSpec`)

The MCP spec is stable per project, whichever dfl binary runs, so every developer writes the same
committed entry:

1. `config.json` `mcp` (`{ command, args }`) when set;
2. `{ command: "npx", args: ["--no-install", "dfl", "mcp"] }` when `<root>/package.json` lists
   `@vishin-pavel/dfl` in `dependencies`, `devDependencies` or `optionalDependencies`;
3. `{ command: "dfl", args: ["mcp"] }` otherwise.

`dflLauncher(paths)` (`src/agents/mcp-config.ts`) applies rules 2–3 to the CLI (`npx --no-install
dfl` or `dfl`) and is used for `dfl.cli` in templates, the MCP authoring guide and CLI/MCP hints.
Sync warns when an entry using `dfl` was written but `dfl` is not on `PATH`. On native Windows
neither `dfl` nor `npx` can be spawned without a shell (`.cmd` shims); the documented workaround is
a `config.json` override (`cmd /c …`, or `node node_modules/@vishin-pavel/dfl/dist/cli.mjs mcp`).

An existing `dfl` entry counts as dfl's own (`isDflLauncher`) when its command is `dfl`, or
`npx`/`pnpm`/`yarn` with a `dfl` (or package name) argument, or exactly the `config.json` override.
Uninstall removes only such entries.

### 4.2 Project root

CLI: `--root` → `DFL_ROOT` (both must be existing directories, else `BAD_ROOT`) → nearest ancestor
of the cwd with `.df/`, but the search never crosses into an enclosing git repository: when a
directory with `.git` (a nested clone or submodule) lies between the cwd and that ancestor, `install`
and `agents` use the nested repository and other commands fail with `NO_PROJECT` (hint:
`--root <outer>`) → (`install` only) git root → cwd.

MCP server: `--root` → `DFL_ROOT` → the client's roots (first `file://` root in or below a
directory with `.df/`; 2026-07-28 clients are asked through an `input_required` result, older
clients with `roots/list`; roots are cached per connection and dropped on `roots/list_changed`) →
nearest ancestor of the server's cwd with `.df/`. `NO_PROJECT` names the cwd and the roots searched.
The nested-repository boundary is not applied here: the server is only started by an agent whose
project MCP config registers it.

## 5. Sync pipeline (`install` / `flow-update` / `flow use` / auto-sync)

`syncProject(paths, opts)` is the single code path that writes outside `.df/`:

1. Resolve the active flow (`NO_ACTIVE_FLOW` when none) and agents
   (`opts.agents ?? local.agents ?? config.agents`; `opts.agents` is persisted to local.json).
2. Validate the flow (errors abort) – before prompting, so an invalid flow never asks questions.
3. Resolve vars; missing required vars → `opts.promptVar(def)` (interactive) or a warning.
4. Render the active flow: every `steps/**/*.md.hbs` → `.md` (inside `.df`). Stale `.md` files are
   deleted only when listed in the previous manifest's `rendered`; step dirs without a state that
   hold only such files are removed; hand-written `.md` files are kept and reported.
5. Render the built-in skills from the package (`templates/skills/*`) in memory (a step with the
   same name wins).
6. For every distinct skills dir: write each skill (rendered `.md` + static non-`.hbs` files) into
   `<skillsDir>/<skillName>/` plus the `.gitignore` marker, subject to the ownership and symlink
   rules of §1.4; stale files of the previous version of that skill are deleted (only files dfl
   wrote).
7. Remove skill dirs of the previous manifest that are no longer produced (deleted steps, switched
   flow, deselected agent) – only the listed files plus the marker; the dir only when empty.
8. MCP entries, when `opts.mcp ?? local.mcp ?? true`: upsert the spec (§4.1) into each selected
   agent's MCP file and record `createdFile`/`createdContainer`. Entries of deselected agents are
   kept (committed team config); with MCP off, existing entries are left alone but still tracked.
   Only `uninstallProject` removes entries.
9. Rewrite `.df/.gitignore`, remove a legacy root `.gitignore` block, write the manifest (with
   `rendered`, `dflVersion` and `fingerprint`).

`dryRun` renders into a temporary copy and reports (`SyncReport`, MCP `status`
`added`/`updated`/`unchanged` via `McpTarget.plan`) without writing or prompting.

### 5.1 Stale skills (`computeSyncFingerprint`, `checkSyncState`)

`fingerprint` = sha256 over: dfl version, active flow name, every file under `.df/<flow>/` except
rendered `.md` outputs (path + content, sorted), the stored vars (defaults, `config.json`,
`local.json`; JSON with sorted keys), the selected agents (sorted), the MCP preference, the launcher
and the project root. Process-environment overrides (`DFL_VAR_*`, `DFL_ENV_*`) are left out: a shell
or MCP client started without them must not see the skills as stale. `checkSyncState(paths)` →
`{ installed, upToDate, reason?, fix? }` (never throws): not installed, unreadable manifest, no flow's
skills installed yet, installed by another dfl version, installed for another flow, fingerprint
mismatch, or a skills dir skipped because of a symlink. `dfl status` (and `status --json` →
`skills`) and MCP `get_status`/`get_flow` (`skills`) report it with the hint to run `dfl flow-update`,
or `fix` when that alone does not help (delete the manifest and `dfl install`; replace the symlink).
`checkFlowSyncState(paths, flow)` is the same for a named flow: a flow that is not active but whose
skills are the installed ones (the active flow changed) gets "run `dfl flow-update`, or
`dfl flow use <flow>`" (`status --flow`, `get_status` with `flow`).

### 5.2 When syncs run

- `dfl install` and `dfl flow-update` (and the MCP `sync` tool) always sync. `dfl install` stores
  the MCP choice (`--mcp`/`--no-mcp` or the wizard answer) in local.json before syncing;
  `flow-update --mcp`/`--no-mcp` applies to one run only.
- Mutations (CLI `step …`, `vars set/unset`, `flow use/create --use/import/pull/delete`, MCP
  `add_step`/`update_step`/`delete_step`) re-sync only when the changed flow is the active one and
  this developer installed dfl (`isInstalledForUser`: the manifest exists and is not marked
  `uninstalled`); otherwise they report "skills not installed for you yet; run `dfl install`".
- `flow use` validates the flow first and restores the previous active flow when the sync fails.
- `flow delete` of the last active flow removes that flow's skills but keeps the MCP entries and a
  manifest without skills, so the project stays installed.

`uninstallProject` removes the manifest's skill files (ownership rules), the `dfl` MCP entries that
look like dfl (only the file/container dfl created) and a legacy root `.gitignore` block; `--purge`
also deletes `local.json`, `state.json` and rendered files. Entries it cannot remove (e.g. invalid
JSON) stay in a manifest marked `uninstalled: true`, so a second `dfl uninstall` retries while
mutations do not re-install anything.

## 6. CLI

```
dfl install [--agents a,b] [--flow <tpl-or-name>] [--yes] [--mcp | --no-mcp] [--project-agents]
dfl uninstall [--purge] [--yes]
dfl flow-update [--dry-run] [--mcp | --no-mcp] [--yes]   # alias: dfl update – re-render + re-install
dfl status [--flow <f>] [--json]     # active flow, current step, events, stale-skill warning
dfl next [event] [--from <step>] [--flow <f>] [--json]   # fire event (default NEXT)
dfl goto <step> [--flow <f>] [--json]                    # jump to a step
dfl reset [--flow <f>] [--yes] [--json]                  # back to initial
dfl flow list | templates
dfl flow use <name> [--project] [--no-sync]
dfl flow create <name> [--from <template> | --steps a,b] [--title <t>] [--description <d>] [--use] [--no-sync]
dfl flow import <git-url|github:owner/repo[/path][#ref]|path> [--name <n>] [--flow <names...>] [--force] [--use] [--no-sync]
dfl flow pull [name] [--rev <ref>] [--dry-run] [--yes] [--no-sync]
dfl flow delete <name> [--yes]
dfl flow validate [name] [--json]    # --json: { valid, flows: [{ flow, valid, issues }] }
dfl flow view [name] [--zoom <0-3>] [--print] [--lr] [--ascii]
dfl step list [--flow <f>] [--json]
dfl step add <id> [--after <step>|--before <step>] [--title] [--description] [--event NEXT] [--template-file <f>]
dfl step edit <id> [--title] [--description] [--rename <new-id>] [--template-file <f>] [--initial]
dfl step remove <id> [--force] [--yes]
dfl step transition <id> <event> [target] [--description <text>] [--remove]
dfl vars list | set <key> <value> [--personal|--project] | unset <key>
dfl agents [--json]                  # supported agents, detection, where skills go
dfl mcp                              # stdio MCP server (global --root <dir> / DFL_ROOT)
```
Global options: `--root <dir>`, `--no-color`, `-v/--version`. Step mutations accept
`--flow <f>` and `--no-sync`; list/status commands accept `--json`.

- Rich output: `@clack/prompts` for wizards/spinners/notes, `picocolors` for colour, Ink (React)
  for the full-screen flow viewer. Warnings go to stderr. Tables fit `process.stdout.columns`, or
  `$COLUMNS` when stdout is not a terminal.
- All commands work non-interactively (`--yes`, stdin/stdout not a TTY, or `CI` set) and exit
  non-zero on error. Destructive commands (`uninstall`, `flow delete`, `flow pull`, `step remove`)
  ask for confirmation interactively and require `--yes` otherwise. `step remove` reports
  `LAST_STEP`/`CANNOT_REWIRE`/new validation errors before asking (`planRemoveStep`).
- A non-interactive `install` with several flows and no active flow fails with `NO_ACTIVE_FLOW`
  (`--flow`) before writing anything.
- `flow pull` (`pullFlow` in `import.ts`) re-imports a flow from its recorded `source` (template →
  the package template; git → URL at `rev` (or `--rev`), recording the new `commit`; local → the
  directory), replacing the flow's files while keeping runtime state and hand-written `.md` files
  under steps/ (not in the manifest's `rendered`, no sibling `.hbs`); a removed current step moves
  (§1.3). It shows the changed and kept files and the move first (dry run), writes nothing when
  nothing changed, and refuses `created` flows and flows without a source (`NO_SOURCE`).
- `flow import` validates every target name and refuses a source that is (or contains) the target
  directory before deleting anything; flows are staged in `.df/.dfl-stage-*` and swapped in through
  a backup, so a failed import leaves existing flows untouched.
- `src/cli.ts` checks `process.versions.node` (>= 22.12, `src/ui/node-version.ts`, no imports)
  before `await import('./run.js')`.

### 6.1 Flow viewer (`dfl flow view`)

Full-screen Ink app (alternate screen). The flow graph is laid out once per zoom
level into a character canvas; the viewport shows the part that fits the
terminal (minus a 1-line header and 1-line footer) and follows resizes.

| key | action |
|-----|--------|
| `w` `a` `s` `d` (or arrows) | pan up / left / down / right by a quarter of the viewport |
| `W` `A` `S` `D` (PgUp/PgDn) | pan a full page |
| `q` | zoom in (more detail) |
| `e` | zoom out (less detail) |
| `l` | toggle top-to-bottom / left-to-right |
| `c` | center the current step |
| `x` | exit (Ctrl+C also exits) |

Layout: elkjs `layered` + orthogonal routing laid out in terminal cells, drawn on a
character canvas. Nodes are fed to ELK in flow order (§2), so acyclic flows draw top to bottom with
the final state last. Zoom levels: `0` one-line `[Title…]` nodes (widened to `[ Title ]` in
top-to-bottom layouts when several edges end on them; left-to-right layouts give each node one
right-side exit and one left-side entry, other edges attach at the top/bottom), `1` 3-row boxes
with the title, `2` cards with title + wrapped description (max 3 lines), `3` cards with title +
full description + the skill command of the selected agents (`/name`, `$name` for Codex). Events
are edge labels, always on the same side of their line; `NEXT` edges are unlabelled. No two edges
share an end cell on the same node side.
Default zoom = the highest level whose canvas fits the terminal, min 1.
The current step is drawn with a heavy border. Non-TTY or `--print` prints the
whole canvas (default zoom 2); `--lr` and `--ascii` (7-bit output, including the interactive
header and footer) work in both modes.

### 6.2 Project lock (`src/core/lock.ts`)

Mutations take a cross-process lock on `.df/.lock` (created with `O_CREAT|O_EXCL`, holding
`{ pid, host, token, at }`): the MCP server for every mutating tool, the CLI around the
read-modify-write and sync of `step`, `vars`, `flow`, `next`/`goto`/`reset`, `install`,
`flow-update` and `uninstall`. Confirmations and required-variable prompts are asked before the lock
is taken (`askMissingVars`; the sync under the lock never prompts). A waiting process retries for
15 s, then fails with `LOCKED`. The holder refreshes the lock file's mtime every 15 s (heartbeat); a
lock whose process is gone (same host) or that was not refreshed for 60 s is taken over. A `.lock` that is not a regular file is never followed or deleted.
The lock is not re-entrant.

## 7. MCP server (`dfl mcp`)

Server name `dfl`, built on `@modelcontextprotocol/server` v2 (zod 4 schemas).
Files are re-read on every call (no caching), so edits and `git pull` are picked up
immediately. Mutating tools auto-sync per §5.2 and report the sync summary (or why no sync ran)
in `sync`/`warnings`. Tools (all return JSON text + `structuredContent`):

| tool | purpose |
|------|---------|
| `get_flow` | active (or named) flow: steps in order, transitions, vars, current step, `skills`; a broken flow returns `current: null` with `problem` and `issues` |
| `list_flows` | all flows + which is active |
| `get_status` | current step, its skill command, available events, history tail, `skills` (`{ installed, upToDate, reason?, warning? }`, §5.1), `repaired` |
| `get_step` | one step: metadata, transitions, template path, rendered skill text |
| `transition` | fire an event (default `NEXT`) → new current step (`repaired` when the stored step was reset first) |
| `complete_step` | fire an event (default `NEXT`) from a given step (checks it is current; the hint mentions stale skills) |
| `goto_step` | jump to a step |
| `add_step` | create step (dir + SKILL.md.hbs + machine wiring), then re-sync; returns `placement` |
| `update_step` | change title/description/template/transitions (`on`: target, `{target, description}` or null)/rename/initial, then re-sync |
| `delete_step` | delete step, rewire transitions (`rewired`, `dropped`), then re-sync |
| `validate_flow` | validation issues |
| `get_authoring_guide` | how to write step templates (context, helpers, rules, example), with this project's launcher |
| `sync` | same as `dfl flow-update` |

- Annotations: read tools are read-only; `update_step`, `delete_step` and `sync` are destructive;
  `transition`, `complete_step`, `goto_step` and `add_step` are non-destructive writes.
- Arguments: `flow` must match the flow-name pattern. Commands in results (`command`,
  `targetCommand`, `next.command`) use `$name` when the client's name (handshake
  `clientInfo.name`, or the 2026-07-28 request envelope) matches `/codex/i`, `/name` otherwise.
- CLI commands in errors, hints and warnings are spelled with the project's launcher
  (`npx --no-install dfl …`). Errors are returned as tool errors with `code` and `hint`. An
  `INVALID_FLOW` hint suggests `validate_flow` + `update_step` only when the flow still loads (a
  machine or validation error); when flow.json itself cannot be loaded (schema, `name` mismatch) it
  says to edit `.df/<flow>/flow.json` directly.
- `add_step`, `update_step`, `delete_step` and `sync` send `notifications/resources/list_changed`
  after success; changes made outside the server are not announced.
- Mutations run one at a time in-process and under the project lock (§6.2) across processes.
- stdout carries only JSON-RPC (`{{log}}` writes to stderr); `DFL_DEBUG=1` logs transport errors
  to stderr.

Resources: `dfl://flow` (active flow JSON), `dfl://steps/{id}` (step template).
