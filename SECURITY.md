# Security Policy

## Supported Versions

Security updates are provided for the latest minor release line:

| Version | Supported |
|---|---|
| `0.3.x` | Yes |
| `< 0.3.0` | No |

## Reporting a Vulnerability

**Please do not report security vulnerabilities through public GitHub issues, pull requests, or discussions.**

Report suspected security vulnerabilities privately via GitHub Security Advisories:

- **Private report**: <https://github.com/vishin-pavel/dfl/security/advisories/new>
- **Fallback email** (if you cannot use GitHub Security Advisories): `it.vishin@gmail.com`

When reporting, please include as much of the following as possible:

- Affected `dfl` version (`dfl --version`), Node.js version, and OS
- Affected component (for example, CLI, MCP server, Jira tracker client, agent config editor, template rendering, or git helpers)
- Step-by-step reproduction instructions or a minimal proof of concept
- Expected impact and any suggested remediation

### Response & Disclosure Timeline

- **Acknowledgment**: Within 3 business days of receiving the report.
- **Triage & initial assessment**: Within 7 business days, including severity assessment and whether the report is accepted.
- **Fix & coordinated disclosure**: We aim to release a patch and publish a security advisory within 30 days for high/critical issues (or on a mutually agreed timeline for complex fixes). Reporters will be credited in the advisory unless they prefer to remain anonymous.

## Security Model

`dfl` executes locally on developer machines and in CI, edits coding-agent configuration files, runs a stdio MCP server, invokes `git`, renders Handlebars templates, and optionally communicates with Jira Cloud. Key security boundaries include:

- **Jira credential isolation**: API tokens are stored outside project repositories in `~/.config/dfl/credentials.json` (`%APPDATA%\dfl\credentials.json` on Windows, or `$DFL_CONFIG_DIR/credentials.json`) with `0600` file permissions (`0700` directory permissions), bound to the exact configured Jira site origin. Tokens are never written into `.df/`, rendered skills, MCP configs, `--json` output, error messages, or debug logs. HTTP requests use `redirect: 'manual'` so Basic auth headers are never forwarded across redirects.
- **Stdio MCP server**: `dfl mcp` communicates exclusively over stdio with the local coding agent process; it does not bind a network port.
- **Filesystem & symlink safety**: Path segments are validated against traversal (`assertPathSegment`), and sync/file operations refuse symlinks to prevent writing outside intended project and agent directories.
- **Prompt-injection & terminal boundaries**: Ticket summaries and task parameters are passed to agents as data rather than instructions; instructions are generated by `dfl` itself. Terminal output sanitizes control characters from external ticket text to prevent terminal escape injection.
- **Git command safety**: All `git` invocations use `execFile` / `execFileSync` without a shell, set `GIT_TERMINAL_PROMPT=0`, validate ref/argument names, and use `--` separators to prevent flag injection.

For operational details on Jira credentials, CI environment variables, and agent sandboxing, see [Credentials, CI and security](README.md#credentials-ci-and-security).
