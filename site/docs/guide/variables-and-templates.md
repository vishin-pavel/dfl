# Flows, Variables, Templates & Sharing

`dfl` turns your team's engineering process into version-controlled files under `.df/`. One flow definition renders native [Agent Skills](https://agentskills.io/specification) into every selected coding agent's skill folder while keeping git history completely clean of personal settings.

---

## How It Works & `.df/` Layout

```text
.df/dev/flow.json                          ─┐
.df/dev/steps/classify-task/SKILL.md.hbs    ├─ dfl install / flow-update ─┬─> .claude/skills/classify-task/SKILL.md
.df/config.json + .df/local.json (vars)    ─┘                             ├─> .cursor/skills/classify-task/SKILL.md
                                                                          ├─> .agents/skills/classify-task/SKILL.md (Codex, Antigravity)
                                                                          └─> .mcp.json, .cursor/mcp.json, … (dfl MCP server)
```

### Directory Structure

```text
<project>/
  .df/
    config.json            # committed   project config: team default flow, project vars, MCP override
    local.json             # ignored     personal config: your agents, personal vars, flow override, MCP preference
    state.json             # ignored     current step and history of each flow (local untracked flows)
    fast-forward.json      # ignored     fast-forward runs for this checkout
    installed.json         # ignored     manifest of files dfl wrote (skills, MCP entries, rendered files)
    tracker.json           # committed   optional: Jira Cloud site, projects, step → status mapping
    .gitignore             # committed   generated by dfl on every sync; ignores personal/runtime files above
    .dfl-backups/          # ignored     automatic snapshots written before flow pull / import --force / delete
    <flow>/
      flow.json            # committed   flat xstate v5 flow definition ("name" must match directory name)
      partials/*.hbs       # committed   optional Handlebars partials for this flow
      steps/<step>/
        SKILL.md.hbs       # committed   Handlebars template for the step's skill
        **/*.md.hbs        # committed   optional extra templated docs (X.md.hbs → X.md)
        **/* (not .hbs)    # committed   static assets copied verbatim (scripts, JSON, images)
        SKILL.md, **/*.md  # ignored     rendered output
```

### Git-Clean Ownership Model

- **Self-ignoring skill folders:** Every installed skill folder (`.claude/skills/<skill>/`, `.cursor/skills/<skill>/`, etc.) receives its own `.gitignore` containing `*`. Git ignores the entire directory (including the marker) without `dfl` ever modifying your repository's root `.gitignore`.
- **Safe ownership tracking:** `dfl` records everything it writes outside `.df/` in `.df/installed.json`. A skill folder you wrote by hand is never overwritten or deleted: `dfl` only treats a directory as managed when it contains dfl's `.gitignore` marker or its `SKILL.md` carries `metadata.dfl-*` frontmatter keys. It deletes only the files it installed and never writes or deletes through symlinks.
- **Sync never mutates flows:** `dfl install`, `dfl flow-update` (`dfl update`), and the MCP `sync` tool only render and install skills — even after upgrading `dfl`. Only one flow is active at a time; `dfl flow use <name>` swaps installed skills cleanly.

## `flow.json` Format (Flat XState v5)

Each flow is a flat [xstate v5](https://stately.ai/docs/xstate) machine configuration:

```json
{
  "name": "feature",
  "title": "Feature development",
  "description": "From spec to shipped PR.",
  "version": "1.0.0",
  "skillPrefix": "",
  "source": {
    "type": "git",
    "ref": "https://github.com/acme/dev-flows.git",
    "path": "flows/feature",
    "commit": "3f2a9c1...",
    "files": {
      "flow.json": "77caab347d357129",
      "steps/spec-feature/SKILL.md.hbs": "d1db6b335b8ee37d"
    }
  },
  "vars": {
    "mainBranch": { "description": "Default branch PRs target", "default": "main", "scope": "project" },
    "reviewer": { "description": "Your GitHub handle for review requests", "scope": "personal", "required": false }
  },
  "machine": {
    "id": "feature",
    "initial": "spec-feature",
    "states": {
      "spec-feature": {
        "description": "Write a feature spec. Use when starting a feature.",
        "meta": { "title": "Spec" },
        "on": { "NEXT": "plan-feature" }
      },
      "plan-feature": {
        "description": "Plan the implementation. Use after the spec is agreed.",
        "meta": { "title": "Plan" },
        "on": {
          "NEXT": "done",
          "BACK": { "target": "spec-feature", "description": "The spec is missing information" }
        }
      },
      "done": { "type": "final", "description": "Feature shipped" }
    }
  }
}
```

### Flat Machine Rules

- **Flat machines only:** Atomic states are steps; `"type": "final"` states are terminal markers. Nested states, parallel states, guards, actions, and transition arrays are not supported.
- **Naming:** Flow names and step IDs are kebab-case (max 64 characters); step IDs need at least one letter (`step-1`, not `1`). `name` must match the directory name. The rendered skill name and slash command is `skillPrefix + id`.
- **Descriptions:** State `description` becomes the skill's YAML frontmatter `description` (start with a verb and state when to use it). Transitions are `"EVENT": "target"` or `{ "target": "…", "description": "…" }`; give every non-`NEXT` event a description so agents know when to fire it.
- **Step order:** Lists, `step N of M`, fast-forward back-edge detection, and `dfl flow view` follow the declaration order in `machine.states`, with `initial` moved first and final states moved last.
- **`source` metadata:** Managed by `dfl` (template, git URL + commit, or local dir + per-file digests) so `dfl flow pull` can distinguish upstream updates from local edits. Do not edit manually.

### Editing Steps

Edit via CLI (`dfl step add|edit|remove|transition`) or via your coding agent using the built-in skills (`/add-flow-step`, `/edit-flow-step`, `/delete-flow-step`). Every mutation is validated **before** writing — edits that introduce validation errors or unparseable Handlebars templates are refused. Existing errors in a broken flow do not block incremental repair.

## Handlebars 4 Templates

Templates use [Handlebars 4](https://handlebarsjs.com/guide/) with HTML escaping disabled. `dfl` automatically generates Agent Skills YAML frontmatter (`name`, `description`, `metadata.dfl-flow`, `metadata.dfl-step`) for `SKILL.md.hbs`. Any custom frontmatter (`license`, `compatibility`, `allowed-tools`, `metadata`) is preserved; `name` is always forced.

### Template Context

| Variable | Value |
|----------|-------|
| `project.name`, `project.root` | Project directory name and absolute path |
| `flow.name`, `flow.title`, `flow.description`, `flow.skillPrefix`, `flow.initial`, `flow.stepCount` | Flow metadata |
| `flow.steps[]` | Non-final steps in flow order |
| `step.id`, `step.skillName`, `step.title`, `step.description`, `step.number` (1-based), `step.index` | Current step being rendered |
| `step.next[]`, `step.prev[]` | Outgoing / incoming transitions (`event`, `id`, `skillName`, `title`, `final`, `description`) |
| `vars.<name>` | Resolved flow variables |
| `env.<NAME>` | Allow-listed `DFL_ENV_<NAME>` environment variable at render time (other env vars are hidden) |
| `dfl.version`, `dfl.mcpServer`, `dfl.cli` | `dfl` version, MCP server name (`dfl`), CLI invocation (`dfl` or `npx --no-install dfl`) |

### Built-in Helpers

- Logic (inline or block): `eq`, `ne`, `and`, `or`, `not` (e.g. `` {{#eq a b}}…{{else}}…{{/eq}} ``)
- Strings & formatting: `default value fallback`, `upper`, `lower`, `kebab`, `title`, `json value`, `join list sep`, `indent n text` (or block `` {{#indent 2}}…{{/indent}} ``)
- Agent helpers: `command skillName` (renders `/skill-name`), `handle value` (strips leading `@` and spaces, e.g. for `gh --reviewer`)
- Debugging: `{{log …}}` prints to `stderr` and renders nothing (keeps MCP `stdout` JSON-RPC clean)

### Partials & Rules

- **End every step template with `{{> flow-context}}`**: Renders the step's position, incoming/outgoing transitions, `get_status` / `complete_step` MCP instructions, CLI fallbacks, and `/fast-forward` instructions. Place custom partials (or an override of `flow-context`) in `.df/<flow>/partials/<name>.hbs`.
- **Literal braces:** Escape literal braces as `\{{` (for example `$\{{ secrets.NPM_TOKEN }}`). `dfl flow validate` warns on unknown root identifiers.
- **Avoid agent macro tokens:** Avoid `$ARGUMENTS`, `$1`, lines starting with `` !` ``, and bare `@word` tokens (Claude Code and OpenCode expand them). Render handles with `{{handle vars.reviewer}}`.
- **File naming:** Only `*.md.hbs` files are rendered. All `.md` files under `.df/<flow>/steps/` are git-ignored as rendered output — always name hand-written reference docs `X.md.hbs`. Non-`.hbs` files (scripts, JSON, images) are copied verbatim.

## Variable Layering

Flows declare variables in `flow.json` under `vars` (`description`, `default`, `scope`, `required`). Values resolve in order — **later wins**:

1. `default` in `.df/<flow>/flow.json`
2. `.df/config.json` `vars` — **project** scope (committed)
3. `.df/local.json` `vars` — **personal** scope (git-ignored)
4. Environment `DFL_VAR_<UPPER_SNAKE_NAME>` (e.g. `DFL_VAR_MAIN_BRANCH` for `mainBranch`)

```sh
dfl vars list                       # show resolved values and sources
dfl vars set mainBranch develop     # saved in its declared scope
dfl vars set reviewer octocat --personal
dfl vars unset reviewer
```

Stored values are shared across all flows in the project. Guard optional variables in templates with `` {{#if vars.reviewer}}…{{/if}} ``.

Run `dfl agents` to see which tools are detected in your project along with per-agent notes.

::: tip Note on Codex Invocation & Shared Folders
Rendered skills use `/name` syntax across all agents; **OpenAI Codex** users invoke skills with `$name` (and MCP tool responses automatically return `$name` when the client identifies itself as Codex). Shared folders like `.agents/skills` and `.mcp.json` are automatically deduplicated during sync.

If your tool reads `.agents/skills` or `.claude/skills`, install for that agent and register the stdio MCP server (`dfl mcp` or `npx --no-install dfl mcp`) in your tool's settings (pass `--no-mcp` to skip writing the built-in MCP config).

## Built-in Skills

Installed automatically with every flow for every selected agent:

| Skill | Purpose |
|-------|---------|
| `/add-flow-step` | Interviews you, drafts `SKILL.md.hbs`, and wires the new step into the active flow via MCP |
| `/edit-flow-step` | Updates a step's title, description, template, transitions, ID, or initial state |
| `/delete-flow-step` | Removes a step and cleanly reroutes incoming transitions |
| `/fast-forward` | Runs flow steps autonomously to a target state or flow end with safety rails (see [The `dev` Flow](/guide/dev-flow#fast-forward-autopilot-fast-forward)) |
| `/init-task` | Installed only when `.df/tracker.json` exists — starts or continues a Jira ticket (see [Jira Cloud Tracking](/guide/jira)) |

All built-in skills fall back to the `dfl` CLI if the MCP server is unavailable. Step IDs cannot collide with `add-flow-step`, `edit-flow-step`, `delete-flow-step`, or `fast-forward` (a step named `init-task` overrides the built-in `/init-task`).

## Sharing Flows, Safe Pulls & Backups

### Sharing Over Git

Commit `.df/` and the agent MCP configs once:

```sh
git add .df .mcp.json .cursor/mcp.json
git commit -m "Add the dev flow"
```

Teammates pull and run `dfl install` once (picking their own agents and personal variables), then `dfl flow-update` whenever flow templates change (`dfl status` warns when skills are stale). Use `dfl install --project-agents` to save default agents for the team, and `dfl flow use <name> --project` to change the team default flow.

### Cross-Repo Import & Export

```sh
# Import from GitHub shorthand, git URL, local dir, or .dfl.json snapshot
dfl flow import github:acme/dev-flows/flows/feature#v1
dfl flow import https://github.com/acme/dev-flows.git#main
dfl flow import ../other-project/.df/hotfix --name hf
dfl flow import github:acme/dev-flows --flow feature bugfix --use

# Export portable snapshots (never includes rendered skills or personal values)
dfl flow export                       # active flow → ./dev.dfl.json
dfl flow export --all -o all.dfl.json
dfl flow import dev.dfl.json
```

### Safe Updates (`dfl flow pull`) & Automatic Backups

Upgrading `dfl` never overwrites your `.df/<flow>/` files. When an upstream template or git source changes, `dfl` notifies you and lets you preview diffs using per-file digests recorded in `source.files`:

```sh
dfl flow pull --dry-run               # preview upstream changes and local edit conflicts
dfl flow pull                         # review, confirm, backup, then update
dfl flow pull dev --yes               # non-interactive only if no local edits are lost
dfl flow pull --yes --discard-local   # explicitly overwrite local edits
dfl flow pull --rev v2                # pull a specific git branch, tag, or commit
```

Before `dfl flow pull`, `dfl flow import --force`, or `dfl flow delete` replaces or removes a flow, `dfl` saves a full snapshot to `.df/.dfl-backups/<flow>-<timestamp>.dfl.json` (git-ignored, never auto-deleted) and prints the exact restore command:

```sh
dfl flow import .df/.dfl-backups/dev-20261001T153000Z.dfl.json --force
```

### Upgrading from Retired Sample Flows

Flows created from the retired v0.1 sample templates (`feature`, `bugfix`, `quick`) continue to work unchanged in `.df/<flow>/`, but `dfl flow pull` and `dfl flow create --from feature` return `TEMPLATE_RETIRED`. To adopt `dev` alongside an existing flow:

```sh
dfl flow create dev --from dev
dfl flow use dev --project
dfl flow delete feature --yes         # once open work finishes (backup saved first)
```
